## B001 · P1：切换页面会丢失防抖窗口内的用户编辑

- **修复状态**：修复成功。

- **位置**：`frontend/src/pages/TranscriptPage.tsx:347-364,376`；`frontend/src/App.tsx:74-82`。
- **触发步骤**：打开一个句段，修改用户文本，在最后一次输入后 700 毫秒内点击“导出”等其他导航页，再返回转录稿。
- **代码证据**：`scheduleSave` 只更新组件内的 `draft`，把真正的 `onPatch` 延迟 700 毫秒。导航改变 `PageContent` 返回的组件类型，卸载转录页；卸载清理直接 `clearTimeout`，没有提交草稿或将待保存内容移交持久的保存队列。

- **预期**：正常导航不能静默丢失已经输入的内容，保存状态应区分待提交、提交中、成功和失败。
- **修复建议**：让待保存任务跨页面存活，或在导航前可靠地提交；保存任务携带固定句段 ID、版本和文本，并对尚未提交及失败状态给出准确提示。

## B016 · P1：并发安装同一 revision 时，失败请求可能删除成功请求的模型

- **修复状态**：修复成功。

- **位置**：`backend/classscribe/models/manager.py` 的 `install_confirmed`；`backend/classscribe/api/routes.py` 的 `confirm_model_install`。
- **触发**：两个不同的有效确认令牌并发安装同一个尚未安装的 model/revision。
- **证据与影响**：API 将确认安装放入线程执行，manager 没有按 model/revision 加锁。两次请求都可能通过 `target.exists()` 检查。第一个请求把非空 payload 移入 target 并完成安装后，第二个请求的 `os.replace(payload, target)` 因目标非空而失败；异常清理却无条件对存在的 target 调用 `shutil.rmtree`，删除第一个请求的成果，并可能改变 active 指针。
- **建议**：串行化同 revision 的安装并明确目录所有权；失败清理只能删除本次请求成功创建的目标，不能删除其他请求占有的目录。

## B017 · P1：回滚在校验旧版本之前修改 active 指针，失败后不恢复

- **修复状态**：修复成功。

- **位置**：`backend/classscribe/models/manager.py` 的 `rollback`、`resolve_for_runtime`。
- **触发**：当前 A 版本可用，旧 B 目录及 supply-chain.json 存在但模型文件损坏，请求回滚到 B。
- **证据与影响**：`rollback` 只检查控制文件存在，随后先 `_activate(B)`，再 `resolve_for_runtime` 完整校验。校验失败抛出异常，却没有恢复 A 指针。调用者收到回滚失败，但原本正常的模型也无法运行。另在安装进程于健康检查前崩溃、留下完整 payload/audit 的情况下，回滚和 runtime resolve 均未要求 audit 中存在成功 health_check，能够启用未完成健康验收的目录。
- **建议**：在不修改 active 的情况下完整校验目标身份、哈希与健康完成记录，最后原子切换；失败保留原 active。

## B019 · P1：350ms 控制超时会让按住听写丢失松开操作

- **修复状态**：修复成功。

- **位置**：`protocol/python/classscribe_protocol/dictation_ipc.py` 的 `DictationIPCClient`；`ibus/engine/classscribe_ibus_engine/controller.py` 的 `handle_key`、`_command`；`ibus/dictationd/classscribe_dictationd/daemon.py` 的 `start`。
- **触发**：按 F9 启动听写，模型/GPU 准备超过默认客户端超时 0.35 秒，之后松开 F9。
- **证据与影响**：控制服务器等 `service.start()` 完成后才响应，而准备过程会等待租约和 worker。客户端超时后 `_command` 把 `_pressed=False`；服务端没有因连接断开取消 begin，仍可稍后启动麦克风。随后释放按键仅在 `_pressed` 为 true 时发送 release，所以这次松开被忽略，可能继续录音直到用户额外取消。

## B020 · P1：失联的听写会话不会释放 core 的全局暂停状态

- **修复状态**：修复成功。

- **位置**：`backend/classscribe/scheduler/ipc.py` 的 `_sessions`、`_handle`；`ibus/dictationd/classscribe_dictationd/daemon.py` 的 `SchedulerLeaseClient._request`、`DictationService.start`、`_release_lease`。
- **触发**：begin_dictation 成功后 dictationd 崩溃；或 core 准备 worker 超过客户端 begin 的 35 秒等待期限，随后准备成功。

- **触发**：音频队列中已有多帧，消费其中一帧时 VAD/ASR 失败；用户随后再次开始听写。

## B003 · P2：按可见句段末尾计算音频比例，导致句段跳转时间错误

- **修复状态**：修复成功。

- **位置**：`frontend/src/pages/TranscriptPage.tsx:151-156`；`backend/classscribe/api/service.py:304-329`。
- **触发条件**：录音末尾存在静音，或者“仅低置信度”筛选使最后一个可见句段早于录音结束。
- **代码证据**：前端取当前返回句段的最大 `end_sample` 作为 `duration`，并调用 `seekTo(segment.start_sample / duration)`。后端开启筛选时确实会剔除其他句段，返回列表不代表全长。波形始终加载完整录音。本地已安装的 WaveSurfer 实现 `dist/wavesurfer.js:474-476` 将该比例乘以完整媒体的 `getDuration()`。
- **数值示例**：完整音频 120 秒，最后一个可见句段结束于 60 秒，目标句段始于 30 秒。当前算法传入 `30 / 60 = 0.5`，播放器定位到 60 秒，而不是 30 秒。此为源码计算示例，未运行验证。
- **实际影响**：句段点击不能可靠定位对应音频，语言和说话人轨道也会因同一错误分母而相对完整波形拉伸。该错误独立于上一项生命周期问题：即使稳定波形实例，计算结果仍然错误。
- **预期**：绝对 16 kHz sample 应映射到固定的录音时间轴，不随句段筛选改变。
- **修复建议**：跳转使用绝对秒数 `start_sample / 16000`；轨道布局使用完整录音的 canonical 时长。
