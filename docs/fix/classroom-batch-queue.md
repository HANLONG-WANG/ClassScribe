# 多课堂批量导入与顺序转录开发计划

日期：2026-09-08。状态：批量导入与串行队列已实施、测试并部署。下方保留设计计划，实施说明见文末。

## 目标与默认行为

一次选择或拖入多节课的音频/视频，逐个上传并加入持久化队列。后台同一时间只执行一个课堂任务，从预处理、ASR、后处理到自动导出全部完成并释放资源后，再处理下一节课。用户可以继续添加课程、浏览历史稿件或关闭浏览器。

默认按用户在待导入列表中确定的顺序先进先出，不按模型类型重新排序。上传可以与当前课堂转录重叠，但上传并发初版固定为 1，课堂执行并发固定为 1。

## 现状与必须解决的问题

- `frontend/src/pages/UploadPage.tsx` 仅维护一个 `File`；文件输入未开启 `multiple`，只读取第一个文件。提交成功直接跳到单任务页。
- 当前客户端用 `AudioContext.decodeAudioData()` 完整解码媒体以取得时长；多节长课若同时解码，会明显增加内存压力。
- `backend/classscribe/api/routes.py` 的上传接口使用 `await request.body()`，将整个文件读入内存；服务随后以完整字节内容写文件。批量长课场景需要流式落盘。
- `ClassScribeService.create_job()` 创建任务后立即调用 `pipeline.schedule()`。
- `ClassroomPipeline.schedule()` 为每次提交创建异步任务并在线程中运行。`_active_jobs` 只防止同一任务重复执行，不能保证不同课堂之间串行；已有 worker 资源管理不能代替明确的 FIFO 课堂队列。
- 已有 SQLite 任务、检查点、暂停/取消、启动恢复、IBus 抢占和历史稿件列表，可复用；不需要引入 Redis 或外部队列服务。

## 用户流程

1. 导入页支持多选、拖放、追加文件。列表展示文件名、大小、上传状态；入队前可以移除文件、调整顺序。
2. 初版一批文件使用同一组语言、模型、精度、词典及导出设置。界面明确提示；不同设置的课程分批加入，提交时冻结每个任务的设置。
3. 点击“加入转录队列”后逐个上传。每个文件上传和校验成功即建立任务并入队，不必等待整批全部上传完才开始转录。
4. 显示“待上传 / 上传中 / 校验中 / 已入队 / 失败”。单个文件失败不阻断后续文件，可单独重试；取消本次导入只停止未完成上传，不取消已经入队的课程。
5. “任务”主导航先展示队列，当前单任务详情保留。显示正在转录的课程、阶段进度、等待序号、队列控制；完成项可以打开转录稿或导出。
6. 明确区分本地待上传文件与后端已接收任务：关闭浏览器后，已入队课程继续；尚未上传完成的文件不会自动上传，重新进入时应能看到可恢复状态及重新选择文件提示。

## 后端设计

### 持久化顺序与状态

- 在任务上增加独立队列顺序字段和入队时间；初版无需修改既有任务状态枚举。`pending` 在队列界面显示“等待转录”，上传状态不冒充课堂任务状态。
- 增加持久化的队列暂停设置。数据库保存顺序与控制状态，内存事件仅用于唤醒调度器。
- 队列顺序通过数据库事务分配，不能仅靠前端数组、文件名、时间戳或无锁 `max+1`。
- 历史已完成/失败/已取消任务不重新入队；迁移时只为符合条件的未完成任务确定顺序，并保留用户暂停状态。
- 为入队请求增加幂等键和唯一约束。上传成功后若响应丢失或创建任务重试，应返回同一任务，避免重复转录。同一文件由用户主动提交新的请求仍可创建新任务，不按文件哈希静默去重。

### 单执行器调度

- 将 `schedule(job_id)` 从“直接启动任务”改为“确认持久化入队并唤醒调度器”，所有新建、恢复、重试和 IBus 恢复入口统一接入。
- 调度器按持久化顺序领取任务，整节课执行结束或让出后，等待 `close_job()` 完成并释放资源，再领取下一节课。
- 使用原子领取与进程级单执行器约束，防止重复唤醒、并发提交或重复启动服务导致一节课运行多次。启动恢复须确认旧执行器已经退出后才能重领任务。
- 最终失败/取消后继续下一个任务；当前任务的已有自动重试策略保持不变。手动重试失败项默认加入队尾。
- “暂停整个队列”：当前课堂在安全检查点暂停，之后不启动新课；恢复时先继续这一课。
- “暂停单个任务”：该课在安全检查点释放资源，队列可以继续其他课；手动恢复时加入队尾。等待项可以直接取消或调整顺序，不硬中断 GPU 推理。
- IBus 抢占时停止派发新课堂，保存被抢占任务及原顺序；释放后优先恢复被抢占任务。不能误恢复用户主动暂停的任务，也不能忽略全局队列暂停。
- 后端重启后优先从检查点恢复意外中断的任务，再按原顺序处理等待项；全局暂停和手动暂停均保留。

### 上传与批次可靠性

- 扩展现有录音上传能力：使用 `request.stream()` 写临时文件，边写边计算 SHA-256、检查大小限制，成功后原子完成录音入库。
- 上传断开、媒体校验失败时清理不完整临时文件，不创建可执行课堂任务；对于已完成录音但尚未建任务的情况，保存可重试的录音 ID，避免重复上传。
- 使用服务端已有媒体探测能力取得真实时长、采样率和声道，不依赖浏览器完整解码每节长课。保留旧上传调用的兼容性，并核对声明信息与实际媒体。
- 为一次批次和每个文件分配稳定标识，保存逐项成功/失败结果；刷新后可查询已上传及已入队结果。浏览器不能恢复文件授权时提示重新选择，不承诺自动续传。
- 前端逐文件上传、释放临时资源；后端执行磁盘/大小限制检查。初版不做分块断点续传或无限上传并发。

### API 规划

- `GET /queue`：队列暂停状态、当前项、等待项与位置、近期结果；较长队列支持分页。
- 队列暂停/恢复接口；等待项调整顺序接口。写操作沿用现有认证和 CSRF 校验，对已运行项重排等冲突返回明确错误。
- 现有 `POST /jobs` 保留单文件兼容，所有入口统一入队，并返回队列状态。
- 批次创建/查询与逐项提交接口用于提交幂等和恢复导入进度；具体 schema 在实施第一阶段定稿，不将整批媒体装入一个巨大 JSON 或内存请求。
- 单任务暂停/取消/重试接口复用并明确队列语义。队列摘要初版定时刷新，单任务进度继续使用现有 SSE。

## 实施顺序

1. **调度与数据迁移**：新增队列字段、持久化暂停、原子领取；替换派发入口，接通恢复、失败继续及资源释放。
2. **批量上传**：流式接收与服务端探测、批次/逐项幂等、前端多文件列表和独立失败重试。
3. **队列界面**：任务列表入口、等待顺序、当前进度、暂停/恢复/取消/重排，与历史稿件页互通。
4. **集成与真实验证**：完成断点、重启、IBus 和媒体验证后，构建前端，确认无运行中的用户任务再重启服务验证。

优先交付完整的“多文件上传→FIFO 串行处理→失败后继续→自动导出”链路；不将重排等辅助功能代替这条核心验收。

## 验收标准

- 一次选择 10 个文件，全部成功接收后可关闭浏览器；后台按确认顺序逐课完成，并分别出现在历史稿件列表。
- A 未释放执行资源前 B 不开始任何课堂处理；同时从两个页面提交、重复请求和重复唤醒也不能造成重叠执行或重复任务。
- 某个上传失败不影响其他文件；某课转录最终失败后下一课继续，错误仍可查看与重试。
- 暂停单课、暂停整队列、取消等待项、取消运行项和恢复的行为符合上述规则；等待项重排不会改变当前任务。
- 上传成功但建任务响应丢失时重试不产生重复；刷新能恢复服务端已接收状态。
- 后端运行中重启后从检查点继续，顺序不丢失，不重跑已完成任务、不误恢复用户暂停项。
- IBus 抢占/释放不会派发多个课堂任务，也不会打乱原有等待顺序。
- 长媒体的浏览器和后端内存不随整批文件总大小线性增长；真实音频和 MP4 均验证。
- 回归现有单文件导入、任务详情、历史稿件、音频播放、自动导出和文本自动保存。

测试分层：数据库迁移与状态机测试；阻塞式假 runner 的并发/释放顺序测试；上传中断及幂等 API 测试；前端批量与队列交互测试；最后使用少量真实媒体完成顺序转录和重启恢复验证。性能验收记录实测内存，不凭模拟测试宣称通过。

## 实施说明

- `Job.queue_order` 保存排队顺序，`submission_key` 使用唯一索引防止重复提交。数据库迁移 `b12d940ac831` 为既有任务按创建顺序填充值，不重跑终态任务；队列暂停状态保存在 `AppSetting`。
- `schedule()` 改为唤醒一个数据库驱动的调度器。任务执行与 `close_job()` 清理全部结束后才派发下一项；正常任务失败沿用检查点重试上限，耗尽后继续下一课。执行器初始化/清理出现未处理异常则暂停队列，避免资源状态未知时继续派发。
- 数据库旁的文件锁阻止第二个执行器在旧进程仍存活时恢复/领取任务。启动时补齐“已建任务但尚未初始化检查点”的中断窗口。
- 单课暂停/恢复/取消、全局暂停/恢复、等待项上移、IBus 抢占恢复均接入串行队列。手动恢复/重试进入队尾，IBus 恢复保持原顺序。
- 新增 `PUT /recordings/{id}/upload` 流式接收并探测真实媒体信息。旧上传接口保留供其他现有调用使用；批量课堂导入不再在浏览器完整解码。
- 导入页支持多选、拖放、追加、入队前移除/上移，逐项上传百分比和错误重试。点击提交即冻结本批设置；导航到其他页面不会终止后台上传。
- 实施时采用逐文件稳定录音 ID 和任务幂等键代替独立的整批服务端协议。导入提示及设置快照保存在当前浏览器的 localStorage，已接收录音/任务持久化到后端；响应丢失时重试先查询固定录音 ID，再使用同一任务提交键。未上传的文件在浏览器重启后需重新选择，跨浏览器不共享这些本地待上传文件。
- 队列页目前展示所有未完成/失败任务，并提供完整顺序用于重排；完成稿件仍使用已有的分页历史页。本次未增加队列分页或分块断点续传。

验证结果：

- 56 项前端测试通过；涵盖多选、调整提交顺序、单文件失败继续、重试幂等键和队列控制。
- 50 项后端相关测试通过；涵盖十课 FIFO、清理阶段互斥、失败继续、全局暂停安全边界、手动恢复队尾、第二执行器拒绝、IBus、迁移升降级、流式上传中断清理以及生产媒体到导出流程。
- Ruff、Mypy、TypeScript、ESLint 及生产构建通过。
- 使用实际约 63.95 MiB、644.6 秒的 MP4，在临时目录执行流式上传与媒体探测；tracemalloc 记录的 Python 峰值分配为 3.74 MiB。此数值不包含浏览器、FFprobe 子进程或神经模型显存，未据此宣称整套程序的总内存上限。
- 浏览器确认批量导入页面和任务队列入口已生效，实际点击全局暂停/恢复成功，验收后恢复为自动运行。
